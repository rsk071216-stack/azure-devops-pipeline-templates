# Migrating from classic release pipelines

Classic (UI-defined) release pipelines are still common in Azure DevOps
organisations that started before YAML. They work, but they are not versioned
with the code, cannot be reviewed in a pull request, and every project copies
and drifts its own definitions. This page maps classic concepts to this library
and describes a low-risk migration path.

## Concept mapping

| Classic release | YAML with this library |
|---|---|
| Build pipeline + artifact | `stages/container-ci.yml` (image digest is the artifact) |
| Release definition | Consumer `azure-pipelines.yml` extending `governance/secure-pipeline.yml` |
| Stage (Dev / Test / Prod) | `Deploy_<env>` stage generated by `stages/aks-promotion.yml` or `Plan_/Apply_<env>` by `stages/terraform-promotion.yml` |
| Pre-deployment approvals | Approval check on the Azure DevOps **environment** |
| Deployment gates (business hours, Azure Monitor, REST) | Environment checks: Business hours, Invoke Azure Function / REST API, Query Azure Monitor alerts |
| Deployment queue settings | Exclusive lock check + `lockBehavior: sequential` |
| Release variables / variable groups per stage | Template parameters per environment; secrets via Key Vault-linked variable groups |
| Task groups | Step and job templates in this repository - versioned, reviewed, tested |
| Agent job / Deployment group job | Deployment job (`jobs/aks-deploy.yml`, `jobs/terraform-apply.yml`) |
| Manual intervention | Approval check (with instructions) |
| Release retention | Pipeline retention policy; run tags (`deployed-<env>`) for audit queries |
| Service principal with secret | Workload Identity Federation service connection (convert in place) |

## Migration path (per application)

1. **Inventory.** Export the release definition JSON (*Releases > ... > Export*)
   and list tasks, variables, gates and approvers. Anything that is an inline
   script becomes a candidate for a library template or a script file in the
   application repository.
2. **Secretless first.** Convert the service connections used by the classic
   release to Workload Identity Federation (*Convert* button). This is
   independent of YAML and immediately removes secrets.
3. **Create environments and checks** with `platform/azure-devops-governance`,
   mirroring the classic approvers and gates. Do **not** enable the Required
   template check yet on resources still used by the classic release.
4. **Run in parallel.** Add the YAML pipeline with deploy stages targeting
   `dev` only. Compare artifacts and deployment results with the classic release
   for a few iterations.
5. **Cut over per environment.** Move `test`, then `prod` to YAML. Disable the
   corresponding classic stage (*Stage > Disable*) rather than deleting it.
6. **Lock in.** Enable the Required template and branch control checks on the
   environments and service connections. From now on the classic release can no
   longer deploy - that is the point.
7. **Clean up** after one release cycle: delete the classic release
   definition, unused variable groups and the old client secrets.

## Typical surprises

- **Gates that call REST APIs** often hide business logic. Move them to an
  Invoke REST API / Azure Function check on the environment, not into a script.
- **Variables scoped to release stages** become per-environment template
  parameters; secrets belong in Key Vault-backed variable groups referenced only
  inside library templates.
- **"Redeploy a previous release"** in classic is replaced by re-running an
  earlier pipeline run's deploy stage (same digest) or by the automatic
  rollback hook.
- **Artifact versions**: classic releases pick a build artifact by version; with
  this library the image digest from the same run is promoted, which removes
  the "wrong artifact deployed to prod" class of incidents.
